# План: оптимизация под 4-ядерное железо (снижение p99, уменьшение 429)

## Контекст

Проект `D:\work\AI\hackathon\proxy` — FastAPI-сервис маскирования/демаскирования персональных данных (ПД) с контрактом `POST /process`. Проект — git-репозиторий (remote `origin` → `https://github.com/gendirit/proxy.git`).

**Железо организаторов:** 4 ядра, 8 ГБ RAM, без GPU.

**Текущее состояние:** RPS ~1775 на 6-ядерной машине (5 воркеров). На 4 ядрах (3 воркера) RPS будет ~1000-1200. Оцениваются latency p99/p95/p50/avg, количество 429 и невалидных запросов.

**Цель:** снизить latency p99 и количество 429 на 4-ядерном железе, оптимизировать под ограниченные ресурсы.

## Решения пользователя

- **Оптимизация блокировок:** пул блокировок (ограниченный, с хэшированием payload_id).
- **Снижение p99 демаскирования:** запись в SQLite через writer-поток (общий кэш, записи доступны всем воркерам сразу).
- **Оптимизация SQLite-записи:** увеличить `FLUSH_THRESHOLD`, уменьшить `FLUSH_INTERVAL`.
- **Оптимизация детекторов:** движок `regex` вместо `re`.
- **Настройка под 4 ядра:** `WORKERS=3`, проверка реального RPS/latency.

## Задачи

### 1. Оптимизация блокировок (пул блокировок)

**Файл:** `store.py` (`SQLiteStore.get_lock`).

- Заменить `self._locks: dict[str, asyncio.Lock]` (создание на каждый payload_id) на **ограниченный пул**:
  ```python
  LOCK_POOL_SIZE = 1024
  self._locks: list[asyncio.Lock] = [asyncio.Lock() for _ in range(LOCK_POOL_SIZE)]
  ```
- `get_lock(payload_id)` → `self._locks[hash(payload_id) % LOCK_POOL_SIZE]`.
- **Эффект:** не создаёт блокировку на каждый id, снижает накладные расходы и 429.
- **Риск:** разные payload_id могут попасть на одну блокировку (коллизия) — незначительное снижение параллелизма, но допустимо.

### 2. Снижение p99 демаскирования (writer-поток)

**Файл:** `store.py`, `main.py`.

- Заменить локальный буфер `_pending` на **очередь + writer-поток**:
  - `queue.Queue` для несохранённых записей.
  - Отдельный writer-поток (`threading.Thread`), который читает из очереди и пишет в SQLite пачками.
  - Записи попадают в SQLite сразу (через writer-поток), доступны всем воркерам.
- `insert_if_absent` → добавляет запись в очередь (быстро, без ожидания).
- `get` → читает из SQLite (записи уже там, т.к. writer-поток пишет сразу).
- **Эффект:** демаскирование не ждёт 200мс (запись уже в SQLite), p99 снижается.
- **Риск:** writer-поток — один на воркер; при сбое процесса записи в очереди теряются.

### 3. Оптимизация SQLite-записи

**Файл:** `store.py`.

- Увеличить `FLUSH_THRESHOLD` с 1000 до 2000 (меньше транзакций).
- Уменьшить `FLUSH_INTERVAL` с 0.2 до 0.1 (быстрее сброс, но чаще транзакции).
- **Эффект:** баланс между производительностью и задержкой записи.

### 4. Оптимизация детекторов (движок regex)

**Файл:** `detectors.py`, `requirements.txt`.

- Добавить `regex` в `requirements.txt`.
- В `detectors.py` заменить `import re` на `import regex as re` (или точечно для горячих регэкспов).
- **Эффект:** `regex` быстрее на сложных паттернах (даты, адреса), снижает CPU-нагрузку.
- **Риск:** `regex` — внешняя зависимость; нужно установить и проверить совместимость.

### 5. Настройка под 4 ядра

**Файл:** `main.py` (`_default_workers`).

- Проверить, что `_default_workers()` на 4 ядрах даёт 3 воркера (`cpu_count()-1`).
- Запустить с `WORKERS=3` и измерить реальный RPS/latency на 4 ядрах (или эмуляция через ограничение воркеров).
- Зафиксировать p50/p95/p99, количество 429.

## Риски

- **Пул блокировок:** коллизии (разные payload_id на одну блокировку) — незначительное снижение параллелизма.
- **Writer-поток:** потеря записей в очереди при сбое процесса; один writer-поток на воркер.
- **Движок regex:** внешняя зависимость; возможны различия в поведении с `re` (нужно проверить).
- **4 ядра:** RPS 2000 маловероятен на 4 ядрах при CPU-интенсивных детекторах. Реалистичная цель — снижение p99 и 429.
