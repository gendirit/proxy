# Критерии приёмки (Acceptance Criteria)

Документ для сверки решения с критериями оценивания из файла
`technical specification/Критерии_оценивания _альфа.pdf`.

> **Формат маскирования.** В исходном ТЗ указан **частичный** формат (например, `И. И. И.`, `45** ****56`). Организаторы позже решили маскировать **полностью** — все символы ПД скрываются (`*`). Наш сервис реализует **полное скрытие**.

## 1. Качество идентификации и маскирования ПДН (0-6)

**Требования из критериев:**
- Покрытие максимум типов ПДН из перечня (полнота — основа балла).
- Маска делает текст нечитаемым и невосстанавливаемым.
- Нет пропусков: ПДН не уходит в LLM в открытом виде.

**Соответствие нашего решения:**
- ✅ Покрыты все 17 типов ПДН из ТЗ (ФИО, даты, паспорт, гражданство, орган выдачи, код подразделения, в/у, адрес, email, телефон, ИНН, карта, CVV, PIN, держатель карты).
- ✅ Полное скрытие (`*`) — текст нечитаем и невосстанавливаем.
- ✅ Проверено 26 тестовыми кейсами (OK=26, FAIL=0).

**Где в документации:** `docs/STATE.md` (раздел «2.1 Идентификация»), `docs/modules/detectors.md`.

## 2. Корректность демаскирования (0-3)

**Требования из критериев:**
- Демаскированный текст совпадает с оригиналом, позиции знаков сохранены.
- Демаскирование доступно только авторизованной/настроенной системе.
- Если демаскирование не реализовано — 0 баллов.

**Соответствие нашего решения:**
- ✅ Демаскирование по `payload_id` (корреляция маскирование → демаскирование).
- ✅ Позиции знаков сохранены (полное скрытие с сохранением длины).
- ✅ Демаскирование ограничено системой (`allow_unmask` в `config.json`).
- ✅ Исправлена межпроцессная консистентность (ожидание сброса буфера).

**Где в документации:** `docs/STATE.md` (раздел «2.3 Демаскирование»), `docs/modules/main.md`.

## 3. Точность отнесения к ПДН и устойчивость к вариациям (0-4)

**Требования из критериев:**
- Ложные срабатывания отсутствуют или минимальны (не ПДН — не маскируется).
- Определение не зависит от регистра.
- Распознаются вариации: форматы дат, дата текстом, разделяющие слова.

**Соответствие нашего решения:**
- ✅ Публичные личности (Пушкин) не маскируются.
- ✅ Адрес отделения Банка не маскируется (исключение по контексту).
- ✅ Независимость от регистра (в т.ч. ФИО в верхнем регистре).
- ✅ Вариации дат (мм.дд.гггг, гггг.дд.мм, дата текстом, словесные дни).
- ✅ Разделяющие слова («серия хххх номер хххххх»).

**Где в документации:** `docs/STATE.md` (раздел «2.2 Маскирование»), `docs/modules/detectors.md`.

## 4. Гибкая настройка и расширяемость (0-4)

**Требования из критериев:**
- Настройка списка систем-потребителей (вкл/откл).
- Настройка перечня типов ПДН и факта маскирования по системе.
- Наличие/отсутствие демаскирования по системе.
- Расширение списка ПДН без переписывания ядра.
- **Обязателен README** — иначе 0 баллов.

**Соответствие нашего решения:**
- ✅ `config.json`: список систем, `enabled`, `pii_types`, `allow_unmask`.
- ✅ Выбор системы по `X-System-Id`, `403` для отключённых.
- ✅ Расширяемость через архитектуру спанов (добавление регэкспов).
- ✅ README есть (`docs/README.md`).

**Где в документации:** `docs/modules/config.md`, `docs/README.md`.

## 5. Производительность и SLA (0-4)

**Требования из критериев:**
- Latency ≤ 0.5 с при RPS 1000 (целевой уровень).
- Обработка крупных текстов (до 100 000 токенов) без падения.
- RPS 2000 при том же latency (повышенный уровень).
- Честная оценка latency с подтверждением метриками.

**Соответствие нашего решения:**
- ✅ RPS ~1478 (цель 1000 достигнута).
- ✅ Latency p50 ~8ms, p95 ~246ms (≤ 0.5с).
- ✅ Обработка до 100 000 токенов (чанкинг по предложениям).
- ⚠️ RPS 2000 — не достигнут (запланировано в этапе 4).

**Где в документации:** `docs/STATE.md` (раздел «Производительность»), `docs/ROADMAP.md`.

## 6. Безопасность, логирование и метрики (0-3)

**Требования из критериев:**
- Логирование выявленных типов ПДН по каждому запросу.
- Метрики Latency / RPS / TPS.
- Ограничение круга систем (allowlist).
- Нет утечек ключей/реальных ПДН в артефактах.
- Корректная обработка ошибок, деградация.

**Соответствие нашего решения:**
- ✅ Логирование типов ПДН (`detected_types` в логах).
- ✅ Метрики Latency / RPS / TPS (`GET /metrics`).
- ✅ Ограничение систем (`config.json`, `X-System-Id`).
- ✅ ПДН не попадают в логи (RedactFilter, JSON без payload).
- ✅ Обработка ошибок (429, 403, 422), healthcheck `GET /health`.

**Где в документации:** `docs/STATE.md` (раздел «Контракт»), `docs/modules/main.md`.

## 7. Расширенные сценарии (0-3)

**Требования из критериев (по 1 баллу за уверенно показанное, максимум 3):**
- Токенизация/детокенизация или замена синтетическими данными.
- Настройка вида маскирования/токенизации под систему.
- RPS 2000 при Latency ≤ 0.5 с.
- Идентификация документов кроме паспорта РФ.
- Контекстное маскирование (маска только при комбинации типов ПДН).

**Соответствие нашего решения:**
- ✅ Токенизация/детокенизация (демо `POST /v1/chat/completions`).
- ✅ Настройка вида маскирования под систему (`mask_mode` в config.json).
- ⏳ RPS 2000 — запланировано.
- ✅ Документы кроме паспорта РФ (загранпаспорт, военный билет, СНИЛС).
- ✅ Контекстное маскирование (`mask_combinations` в config.json).

**Где в документации:** `docs/ROADMAP.md` (этап 4), `docs/modules/config.md`.

## 8. Качество демо и презентации (0-3)

**Требования из критериев:**
- Короткое объяснение принципа работы и архитектуры (1-2 минуты).
- Схема: Система-потребитель → Модуль → LLM → Потребитель.
- Лаконичные, аргументированные ответы.

**Соответствие нашего решения:**
- ⏳ Презентация не подготовлена (запланировано в этапе 5).

**Где в документации:** `docs/ROADMAP.md` (этап 5).
