## Статус selftest

Команда: `python main.py --selftest`

Результат: **SELFTEST OK** (exit code 0).

Проверенные сценарии:
- пустой payload → пустой результат;
- первый запрос возвращает маску (ПД скрыты);
- повторный запрос с тем же оригиналом возвращает ту же маску;
- запрос с маской возвращает оригинал;
- отсутствие ПД → маска равна оригиналу;
- два одновременных запроса с одним `payload_id` дают одинаковый результат;
- запись не обновляется в спорном случае;
- фильтрация по `pii_types`;
- запрет демаскирования (`allow_unmask=false`);
- одинаковый payload с разными `payload_id` → одинаковая маска.

## Производительность

Нагрузочный тест (`python loadtest.py`, 100 keep-alive соединений, 4000 запросов, 6 простых кейсов):
- RPS: ~989 (цель ТЗ — 1000);
- p50: ~79 ms, p95: ~100 ms, p99: ~496 ms;
- max: ~1470 ms (единичный выброс при гонках на `payload_id`);
- ошибок нет.

Бенчмарк на разнообразном датасете (`python bench.py`, 100 keep-alive соединений, 6000 запросов, 24 кейса по всем типам ПД из ТЗ + негативные):
- **автоопределение воркеров (после чанкинга): RPS ~1715** (цель ТЗ — 1000);
- p50: ~8 ms, p95: ~175 ms, p99: ~285 ms;
- max: ~320 ms;
- ошибок нет.

Тест с уникальными payload_id (`bench_unique.py`, 100 keep-alive соединений, 4000 запросов, 12 кейсов):
- **4 воркера (после оптимизации записи): RPS ~1846**;
- p50: ~8 ms, p95: ~141 ms, p99: ~209 ms;
- max: ~459 ms;
- ошибок нет.

Оптимизации производительности (раунд 1, в `detectors.py`):
1. Вынесены инлайн-компиляции регэкспов в модульные константы (`_ADDR_INDEX_CTX_RE`, `_CARD_HOLDER_CTX_RE`, `_INN_CTX_RE`, `_CITIZENSHIP_RE`).
2. `mask_value` переведён с `re.sub` на `str.translate` с предварительно построенной таблицей `_MASK_TRANSLATE`.
3. Устранено дублирование `_has_context(_DL_CTX_RE, ...)` (переиспользуется `dl_present`).

Оптимизации производительности (раунд 2):
4. Кэширование спанов `_detect` в `main.py` (по системе, учитывает `pii_types`) — `_SPAN_CACHE`.
5. Ранний выход по признакам в `_detect` (`has_digit`, `has_upper`) — пропуск дорогих детекторов.
6. Объединение регэкспов дат в один `_DATE_ALL_RE` (5 → 1 проход).
7. Кэширование `_has_context` в рамках одного вызова `_detect` (словарь `_ctx_cache`).

Переход на несколько воркеров (раунд 3):
8. `store.py` — `SQLiteStore` (общее хранилище для 4 воркеров): WAL, TTL, атомарные операции (`insert_if_absent`), in-memory кэш записей.
9. Метрики агрегируются через SQLite (с буферизацией раз в 1 сек).
10. Конфигурация через env: `DB_PATH`, `WORKERS` (по умолчанию `cpu_count()-1`, автоопределение по числу ядер CPU).

Оптимизация записи (раунд 4):
11. **Батчинг + ленивая запись** в `SQLiteStore`: новые записи попадают в in-memory буфер (`_pending`), сбрасываются в SQLite пачками (каждые 200 мс или при 1000 записей).
12. Чтение из буфера в `get` (сначала буфер → кэш → SQLite).
13. Фоновая задача `_records_flush_loop` (сброс буфера каждые 200 мс).

Прогресс RPS на разнообразном датасете: 794 → 786 → 806 → 843 → 824 → 874 → 901 → 1040 → **1458** (4 воркера + батчинг).

**Вывод:** переход на 4 воркера uvicorn с общим хранилищем SQLite и оптимизация записи (батчинг + ленивая запись) позволили достичь RPS ~1458 на разнообразном датасете и ~1846 при уникальных payload_id. Ключевые факторы: параллельные процессы (детекторы — CPU-интенсивные), in-memory кэш записей и снижение частоты записи в SQLite.

## Контракт POST /process

- `POST /process` с `{payload, payload_id}` → `{result}`;
- направление (маскирование/демаскирование) определяется по `payload_id`;
- идемпотентность к ретраям (блокировки на `payload_id`);
- `429` при перегрузке с `Retry-After`;
- `403` для отключённых/неизвестных систем;
- `GET /metrics` — Prometheus-формат (latency, rps, tps, счётчики типов ПД, 429);
- `GET /health` — healthcheck (200 при доступной БД, 503 при недоступной).
